# CKV_AWS_195: Ensure Glue component has a security configuration associated
## Severity
**LOW** (score: 2.0/10)

Missing a Glue security configuration means data processed by crawlers, dev endpoints, and jobs may be left unencrypted at rest/in transit and CloudWatch logs unencrypted, a moderate confidentiality gap rather than a direct exposure path.

## Summary
Ensures that AWS Glue crawlers, dev endpoints, and jobs have a Glue Security Configuration attached, so that data at rest and in transit within the Glue component is encrypted.

## Applicability
**Checkov framework(s):** `cloudformation`, `terraform`

- **Terraform**: `aws_glue_crawler`, `aws_glue_dev_endpoint`, `aws_glue_job` — inspects the `security_configuration` attribute.
- **CloudFormation**: `AWS::Glue::Crawler`, `AWS::Glue::DevEndpoint`, `AWS::Glue::Job` — inspects `Properties/CrawlerSecurityConfiguration` (Crawler) or `Properties/SecurityConfiguration` (DevEndpoint, Job).

## Why it matters
AWS Glue components process and move potentially sensitive data between data stores (S3, RDS, JDBC sources, etc.). Without a Glue Security Configuration, Glue does not encrypt:
- CloudWatch Logs generated by jobs and crawlers (which can contain data samples, stack traces, or connection metadata),
- Job bookmark data,
- S3 data written by ETL jobs (via SSE-S3/SSE-KMS enforcement),
- Data at rest on the dev endpoint or job's Spark UI / notebook storage.

Leaving these unencrypted increases the blast radius if the underlying S3 buckets, CloudWatch log groups, or EC2/Zeppelin backing infrastructure for a dev endpoint is ever exposed or misconfigured with overly broad IAM/resource policies. It's also a common compliance requirement (e.g., PCI-DSS, HIPAA) that data processing pipelines encrypt data both in transit and at rest, including intermediate logging and bookmark state.

## How Checkov evaluates this
This is a `BaseResourceValueCheck` that inspects a single attribute and expects `ANY_VALUE` (i.e., any non-empty value is acceptable — it does not validate that the referenced Security Configuration itself enables encryption for logs/S3/bookmarks).

- Terraform: checks `security_configuration` is set to any value → PASS; unset → FAIL.
- CloudFormation:
  - `AWS::Glue::Crawler` → checks `Properties/CrawlerSecurityConfiguration`.
  - `AWS::Glue::DevEndpoint` / `AWS::Glue::Job` → checks `Properties/SecurityConfiguration`.
  - Missing/empty → FAIL.

Note: the check only verifies a security configuration is *referenced*, not that the referenced `aws_glue_security_configuration` resource itself has meaningful encryption settings (e.g., `cloudwatch_encryption`, `job_bookmarks_encryption`, `s3_encryption` set to something other than `DISABLED`). Review the referenced security configuration resource separately.

## Non-compliant example
```hcl
resource "aws_glue_job" "etl_job" {
  name     = "sensitive-data-etl"
  role_arn = aws_iam_role.glue_role.arn

  command {
    script_location = "s3://my-scripts/etl.py"
  }
  # No security_configuration set -> FAILS CKV_AWS_195
}
```

## Remediated example
```hcl
resource "aws_glue_security_configuration" "etl_secconf" {
  name = "etl-security-config"

  encryption_configuration {
    cloudwatch_encryption {
      cloudwatch_encryption_mode = "SSE-KMS"
      kms_key_arn                = aws_kms_key.glue_key.arn
    }
    job_bookmarks_encryption {
      job_bookmarks_encryption_mode = "CSE-KMS"
      kms_key_arn                   = aws_kms_key.glue_key.arn
    }
    s3_encryption {
      s3_encryption_mode = "SSE-KMS"
      kms_key_arn         = aws_kms_key.glue_key.arn
    }
  }
}

resource "aws_glue_job" "etl_job" {
  name                = "sensitive-data-etl"
  role_arn            = aws_iam_role.glue_role.arn
  security_configuration = aws_glue_security_configuration.etl_secconf.name  # fix

  command {
    script_location = "s3://my-scripts/etl.py"
  }
}
```

## Remediation steps
1. Create an `aws_glue_security_configuration` (or `AWS::Glue::SecurityConfiguration` in CloudFormation) that enables `cloudwatch_encryption`, `job_bookmarks_encryption`, and `s3_encryption`, using a KMS CMK where possible.
2. Reference that security configuration from every `aws_glue_crawler`, `aws_glue_dev_endpoint`, and `aws_glue_job` via the `security_configuration` attribute (Terraform) or the corresponding `*SecurityConfiguration` property (CloudFormation).
3. Ensure the IAM role used by Glue has `kms:GenerateDataKey`/`kms:Decrypt` permissions on the referenced KMS key.
4. Re-run existing crawlers/jobs after attaching the configuration — encryption settings apply to future runs, not retroactively to existing logs/output.
5. Double-check the security configuration's individual encryption modes are not set to `DISABLED`, since this check only confirms a reference exists, not that encryption is actually turned on inside it.
